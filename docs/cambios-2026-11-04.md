## Errores encontrados y cómo se resolvieron

Ninguno de estos errores era visible sin poner el sistema a funcionar de verdad. Cada uno se descubrió durante la operación y se arregló en el momento.

### 1. Los programas "normales" fallaban dentro del mount

**Síntoma:** al crear una carpeta o copiar archivos dentro del filesystem protegido, herramientas comunes fallaban con `Function not implemented`. La recolección de datos benignos moría en la primera ronda.

**Causa:** a Guardian le faltaban implementar varias operaciones básicas de filesystem (cambiar permisos, cambiar dueño, tocar fechas, borrar carpetas, entre otras). Sin ellas, el kernel le contesta "no implementado" al programa. Además, el daemon le sumaba su propia máscara de permisos a la del usuario, con lo que los archivos quedaban con permisos distintos a los pedidos y las herramientas intentaban corregirlos… con la operación que faltaba.

**Arreglo:** se implementaron las 10 operaciones faltantes como passthrough directo al disco real, y el daemon ya no aplica su propia máscara (la del usuario ya fue aplicada por el sistema antes de que llegue el pedido).

### 2. El listado de carpetas mostraba archivos "fantasma"

**Síntoma:** `ls` dentro del mount mostraba archivos con permisos `000`, dueño `root` y fecha "1 de enero de 1970" (que ni siquiera existían así en el disco). Peor: al copiar una carpeta **desde** el mount con `rsync`, los archivos copiados heredaban esos permisos rotos — y una carpeta con permiso 000 no se puede ni borrar.

**Causa:** cuando Guardian lista una carpeta, le pasa al kernel una descripción incompleta de cada archivo (solo el tipo, sin permisos, dueño ni fechas). El kernel confía en esa descripción y la guarda en caché por un segundo. Todo lo que se consulte en ese segundo ve la información incompleta — y las herramientas de copia la replican.

**Arreglo:** ahora cada archivo se describe completo (con todos sus datos reales) antes de entregarlo al kernel.

### 3. Se perdían las ventanas de datos más valiosas

**Síntoma:** durante la recolección, los ataques aportaban ~1 fila de datos por ronda en lugar de las ~3 esperadas, y los últimos workloads de cada ronda benigna desaparecían del dataset. Una fila con datos "imposibles" (entropía alta sin renombrados) jamás aparecía.

**Causa:** cuando el analyzer no podía entregar el resumen de una ventana (por ejemplo, porque el intermediario que anota los datos se estaba reiniciando entre rondas), la descartaba y empezaba de cero. Se perdía justamente lo más interesante: las ventanas de un atacante recién detectado y matado.

**Arreglo:** ahora, si la entrega falla, la ventana se guarda y se reintenta cuando la conexión vuelve (con un plazo máximo de 30 segundos para no acumular basura si el servidor nunca vuelve). Resultado: los ataques pasaron a aportar ~3 filas por ronda. Los tests del analyzer se actualizaron a este comportamiento nuevo.

### 4. El servidor ML perdía una carrera al arrancar

**Síntoma:** una recolección completa abortaba al arranque con "ML server failed to create socket", sin ningún error visible en el log.

**Causa:** con los modelos ya entrenados, el servidor Python tarda unos 5 segundos en cargar sus bibliotecas antes de estar disponible. El script de recolección solo esperaba 5 segundos exactos: a veces ganaba, a veces perdía.

**Arreglo:** el tiempo de espera subió a 15 segundos.

### 5. Al modelo le faltaban clases de ejemplos (falsos positivos reales)

**Síntoma:** con el primer modelo entrenado, el sistema marcaba como "ataque" a programas claramente benignos:
- un escritor de bloques idénticos (patrón heartbeat / páginas de base de datos): 0.76 de probabilidad de ataque;
- un gzip de archivo grande (backup comprimido): 0.94.

**Causa:** no eran errores del algoritmo sino huecos del dataset. Resulta que:
- En los datos, la única situación con entropía "constantemente pareja en el tiempo" eran los ataques → el modelo aprendió esa firma como sospechosa.
- Los ejemplos benignos de compresión eran de archivos chicos: nunca acumulaban suficientes escrituras por ventana para siquiera entrar al dataset. La clase "escribir mucho datos muy revueltos sin ser atacante" directamente no existía en los datos.
- Además, el gzip del dataset usaba contenido muy repetitivo, que se comprime 40 a 1: producía una sola escritura y nunca generaba fila.

**Arreglo:** se ampliaron las rondas benignas con los casos difíciles (compilar, git, rsync, logs en paralelo, bloques idénticos, archivos de puros ceros, gzip de datos **incomprimibles** de 3 MB — que simulan archivar fotos, videos o backups ya comprimidos). Se reentrenó con el dataset completo y ambos falsos positivos desaparecieron (0.76 → 0.22 y 0.94 → 0.43, ambos "normal").

### 6. Hallazgo documentado (pendiente de decisión)

Durante las pruebas de recolección se vio que un `rsync` masivo dentro del mount dispara la regla de renombrados del detector rápido (los archivos temporales `.archivo.XXXX` → `archivo` cuentan como cambio de extensión). En modo real, ese rsync sería bloqueado aunque el ML opine que es normal — por diseño, el ML puede confirmar ataques pero no vetar bloqueos del detector. Quedó anotado en `docs/pending.md` como decisión de diseño pendiente (¿subir el umbral de renombrados? ¿ignorar sufijos temporales conocidos?).

## Métricas del modelo final

Evaluación con separación por sesiones (las ventanas de una misma corrida nunca se reparten entre entrenamiento y evaluación — evita que el modelo "se copie la respuesta"):

| Modelo | ROC-AUC (validación cruzada) | ROC-AUC (holdout) | Falsos positivos | Falsos negativos |
|---|---|---|---|---|
| Random Forest | 1.0000 | 1.0000 | 0.0% | 0.0% |
| XGBoost | 1.0000 | 0.9997 | 0.0% | 1.4% |

Verificación sobre datos reales (no sintéticos):

- 80 de 80 ventanas benignas del dataset → clasificadas "normal".
- 80 de 80 ventanas de ataque → clasificadas "attack".
- 50 de 50 ventanas de compresión (entropía > 7, la clase difícil) → "normal".

Prueba de punta a punta contra el filesystem real:

- **Ataque simulado:** escritura con entropía 7.99 → bloqueo del renombrado → proceso muerto → snapshot de emergencia creado → el ML confirma "attack" con la ventana del atacante.
- **Workload benigno** (30 documentos de texto + gzip de 3 MB): pasa completo, sin bloqueos, el ML opina "normal".

> **Lectura honesta de estas métricas:** el dataset se genera con un simulador, así que ataque y benigno son más "separables" que en la vida real. El valor de estas métricas es que el pipeline completo funciona y aprende correctamente las clases difíciles; no que el sistema esté "terminado".

## Qué quedó andando y cómo usarlo

```bash
# Verificar que el filesystem protegido sigue montado
mountpoint /mnt/protected

# El servidor ML con los modelos entrenados (si se reinició la VM):
.venv/bin/python src/ml_server.py &

# Ver la evidencia de eventos en tiempo real:
sudo tail -f /var/log/guardian/events.jsonl

# Snapshots tomados:
sudo zfs list -t snapshot tank/data

# Volver a un punto en el tiempo:
sudo ./scripts/rollback.sh tank/data latest

# Más datos + reentrenar (iterar el modelo):
./scripts/collect_training_data.sh 25
.venv/bin/python src/train_model.py
```

Todo el detalle operativo paso a paso está en el [`README.md`](../README.md) y en [`docs/testing-guide.md`](testing-guide.md).
